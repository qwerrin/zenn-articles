## はじめに

プログラミング学習を始めて最初に気づいたのは、「記録しないとすぐ忘れる」という事実でした。

昨日やったこと、詰まったこと、解決した方法——翌朝にはもう半分くらい飛んでいます。Obsidianで書いてみたこともあったのですが、ノートとリンクが増えるにつれて「あれどこだっけ」が頻発して、結局使わなくなりました。

そこで今週、**GitHubに学習ログ専用のリポジトリを作って、続けるための仕組みを整えました**。

実はこの記事、もともとはCSSの学習まとめを書く予定でした。でも「仕組みを作ったこと」の方が今の自分にとって大きな出来事だったので、テーマを変えることにしました。CSSの話は次回に持ち越します。

まだ1週間ですが、「記録が自然に積み上がっていく」感覚があって、思った以上に良かったのでまとめます。

## なぜObsidianじゃなくてGitHubにしたのか

最初に使っていたのはObsidianでした。Markdownで書けるし、ノート同士をリンクできるし、オフラインで動くし、ツールとしては優秀です。ただ、自分の使い方には合いませんでした。

Obsidianの問題は「自由度が高すぎる」ことでした。どこに何を書いてもいい分、ノートが増えるにつれて構造が崩れていきます。「今日の学びはどのノートに書く？」と迷うたびに記録のハードルが上がり、気づいたら開かなくなっていました。

最終的にGitHubに移した理由は3つあります。

**① Markdownで書けてコードも貼りやすい**  
Obsidian同様Markdownで書けるので移行コストはほぼゼロ。さらにGitHub上ではシンタックスハイライトが効くので、コードスニペットをそのまま貼っても読みやすい形で残せます。

**② コミット履歴が"草"になる**  
GitHubの草（コントリビューショングラフ）は、学習した日が視覚的に残ります。「今日も草を生やした」という小さな達成感が継続のエンジンになります。

**③ publicにすることで適度なプレッシャーが生まれる**  
誰かに見られているかもしれない、という意識が雑な記録を防いでくれます。また、Zenn記事を書くときの一次情報（自分の実体験）の蓄積場所にもなります。

## 作ったリポジトリの構造

リポジトリ名：[nana-learning-log](https://github.com/qwerrin/nana-learning-log)

```
nana-learning-log/
├── README.md                # 目標・進捗サマリー・学習チェックリスト
├── weekly-log/              # 週次ログ（日々追記）
│   ├── _template.md
│   └── 2026-W21.md
├── monthly-review/          # 月次振り返り
│   └── _template.md
├── learnings/               # 技術別の学び蓄積
│   ├── _template.md
│   └── html-css.md
├── x-operation/             # X（旧Twitter）投稿テンプレ
│   └── templates.md
├── sandbox/                 # 演習コードの置き場
├── materials/               # 学習資料
└── _templates/              # テンプレート集
```

フォルダを分けたのは「粒度が違う情報を混ぜない」ためです。日々の記録（weekly-log）と技術の学び蓄積（learnings）は目的が違うので、分けて管理するほうが後から探しやすくなります。

## テンプレートを作って「書く内容を迷わないようにした」

毎週ゼロから書こうとすると、「何を書けばいいんだっけ」で止まります。そのため、週次ログのテンプレートを作りました。

```
# Week XX (YYYY/MM/DD 〜 YYYY/MM/DD)

## 🎯 今週の目標
- [ ] 

## 📝 学んだこと（日別）
### 月曜
-
### 火曜
-
...

## 💻 書いたコード
## 📰 公開した発信
## 😅 詰まったこと・失敗   ← ここが大事
## ✨ 来週やること
## 📊 振り返り（5段階）
## 💡 土曜記事のネタメモ
```

特に「😅 詰まったこと・失敗」の欄は意図的に設けています。エラーや勘違いは**Zenn記事のネタになる宝の山**で、記事の「一次情報」として一番価値があるからです。

さらに、**GitHub Actionsで毎週月曜0時に新しい週次ログを自動生成**する仕組みも作りました。月曜の朝に「今週のファイルがもう作られてる」状態にすることで、記録を始めるハードルをゼロにしています。

## 1週間使ってみてどうだったか

実際に使ってみると、想定外の使い方が生まれました。

**学んだことを書くとクイズへの対応力が上がった**  
水曜日にセマンティックHTMLの学びを細かく書いておいたら、金曜日の理解確認クイズで「あ、これ書いた」と思い出せました。書くこと自体が復習になっています。

**詰まったことが「財産」に変わる感覚がある**  
今週詰まったのは「`min` はnumber用で、テキストの文字数制限は `minlength`」という細かいところでした。最初はただのミスですが、ログに書いておくと「初心者がよく間違えるポイント」として記事に使えます。

**設定ファイルの矛盾を整理する副産物もあった**  
複数のドキュメントに同じ情報を書くと矛盾が起きる——これはコードだけでなく、学習管理ファイルでも同じでした。README・CLAUDE.md・週次ログで「学習順序」がバラバラになっていたのを修正したのが今週の大きな作業のひとつです。

## まとめ

GitHubで学習ログを仕組み化して良かったのは、「続けるための摩擦を徹底的に下げた」ことです。

*   テンプレートで「何を書くか」を迷わない
*   GitHub Actionsで「ファイルを作る」作業をなくす
*   publicにすることで記録の質が上がる

まだ1週間なので「本当に続くか」はこれからです。**1か月運用してみたら、続けてわかったことを振り返り記事として書きます**。

もし同じように「記録が続かない」と悩んでいるなら、ぜひリポジトリの構造だけでも参考にしてみてください。
